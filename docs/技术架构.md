# Focus Stack Assistant 技术架构

本文对应当前源码中的两种合成模式。面向维护者，说明从照片扫描到结果发布的实际调用链、两套后端的算法、配置、故障处理和验证方法。

## 1. 模式与边界

| 界面名称 | 配置值 | 实现 | 外部程序 |
| --- | --- | --- | --- |
| 高质量合成（默认） | `quality` | 全分辨率内存对齐、焦点标签、灰色边缘稳定化、窄缝 RGB 融合 | 无 |
| 实验模式（Hugin / Enfuse） | `hugin_enfuse` | Hugin 对齐为 TIFF，生成焦点蒙版，再由 Enfuse 融合 | `align_image_stack`、`enfuse` |

两种模式只在合成阶段分叉；扫描、分组、智能选片、任务调度、结果命名、清单和可选归档均共用。运行中不会在一种后端失败后静默切换到另一种后端。界面原“快速合成”入口现为实验模式，并调用原 Hugin/Enfuse 实现。旧配置值 `opencv` 和 `fast` 映射到 `quality`，`experimental` 和 `hugin` 映射到 `hugin_enfuse`；规范化集中在 `focus_stack_app/fusion_modes.py`。

## 2. 模块与数据流

```text
main.py / focus_stack_app.app
        │
        ▼
ui/main_window.py ──► ApplicationOptions / AppConfig
        │                         │
        └──────────────► ApplicationController
                                  │
               scanner → scene grouping → GroupAnalyzer
                                              │
                             selected_paths + preview_transforms
                             preview_reference + alignment_order
                                              │
                              PipelineCoordinator / bounded queue
                                              │
                                   StackMergeService
                                      ├── quality
                                      └── hugin_enfuse
                                              │
                           result → manifest / SQLite → optional archive
```

主要职责：

- `core/scanner.py`：读取照片和 EXIF；`core/scene_detector.py`、`core/group_detector.py`：场景边界与焦点组。
- `core/group_analyzer.py`：对每组调用 `core/whole_frame_selection.py`，产出选片、参考帧、预览对齐矩阵及 Hugin 输入顺序。
- `pipeline/application_controller.py`：路径、磁盘空间、数据库、缓存、恢复和用户事件；`pipeline/coordinator.py`：分析生产者、有限队列及合成消费者。
- `pipeline/merge_worker.py`：按选择结果调用后端，验证输出，更新状态与清单，最后按选项归档原片。
- `fusion/backends.py`：`QualityFusionBackend`、`HuginEnfuseBackend` 和统一的 `FusionResult`；`fusion/focus_masks.py`：焦点标签及窄缝融合；`fusion/quality_fusion.py`：灰色边缘标签稳定化。
- `storage/database.py`、`storage/manifest.py`：SQLite 状态和 `stack_manifest.csv`；`hugin/`：外部工具发现、运行、对齐、Enfuse 与输出编码。

## 3. 共用的分组与选片

默认只扫描输入目录的 JPEG；递归扫描和隐藏文件由界面选项控制。自动分组结合拍摄时间与画面变化；拍摄暂停阈值可在界面调整，默认 20 秒。默认最少 3 张才能作为合成组，单张、过短或重复组仍会分类，但不执行合成。

选片使用全画面的焦点覆盖策略：先在缩小图上找参考帧和可对齐照片，再逐步加入带来新清晰区域的照片。它返回 `selected_paths`、`selected_indices`、`preview_reference`、`preview_transforms`、`analysis_shapes`、`alignment_order` 和 `capture_order`。这些字段属于同一次分析结果，后端不得自行改变选片集合。质量模式使用预览矩阵；实验模式使用选片顺序及 Hugin 的对齐顺序。合成文件名仍取整组首张原片的文件名，与参考帧是否为首张无关。

## 4. 高质量模式：`quality`

入口为 `QualityFusionBackend.fuse()`，实现分为五步：

1. **确定坐标系**：读取分析阶段的源图到参考图矩阵和相应预览尺寸，换算成原图坐标。恢复任务缺少尺寸元数据时，在最长边 640 像素的图上重新配准；配准失败则报错，不把错误矩阵套到原图。
2. **全尺寸对齐**：逐张解码原图，以参考帧的宽高为目标用 `cv2.warpPerspective` 对齐；插值为 `INTER_LANCZOS4`，边界使用反射填充。对齐图只存内存，不生成一组中间 TIFF。
3. **选择焦点来源**：`build_focus_labels()` 在输出分辨率计算每张图的细节响应，以 Laplacian 局部细节和邻域支持决定每个像素的来源。平坦背景的稳定化逻辑避免让噪声随帧切换。
4. **整理灰色边缘**：`stabilize_neutral_labels()` 仅对参考图灰度小于 235、通道差小于 65 的区域，使用 15×15 中值滤波整理零散的焦点来源编号。此步骤修改的是标签，不对 RGB 图像做 15 像素模糊；彩色区域沿用原焦点判断。
5. **合成与编码**：`blend_focus_pyramid()` 默认 `levels=1`，对各来源的标签边界做约一像素的高斯过渡，再按权重合成 RGB。输出可选 JPG 或 TIFF；默认 JPG 使用质量 100、4:4:4 采样。

`AlignedFrameCache` 在内存预算内复用已对齐图，内存不足时放弃复用并重新解码。参考帧的边缘判断通过只读 `peek()` 取得，不提前消耗融合阶段缓存。每组合成完成、取消或异常后都会释放该缓存。

质量模式主要针对测试中灰色齿尖和黑色杆边缘的碎块、重影。它不能凭空恢复原片不存在的清晰细节；预览级全局变换也无法完全校正物体运动或明显视差。

## 5. 实验模式：`hugin_enfuse`

入口为 `HuginEnfuseBackend.fuse()`。它按分析提供的顺序调用 `align_image_stack`，对齐结果保存为组内临时 TIFF。后端检查输出数量、尺寸、裁切比例和主体几何一致性；可在独立目录中按不同参数重试，必要时改用完整拍摄顺序。超过 20 张且拍摄顺序完整时，首次尝试优先使用拍摄顺序。

对齐通过后，`hugin/enfuse.py` 默认在全分辨率 TIFF 上生成焦点标签并写入硬蒙版，由 Enfuse 读取蒙版完成融合。融合层数可以显式配置；自动配置会根据平坦区域的明暗漂移选择层数。Enfuse 先写私有临时 TIFF，编码完成后才发布最终结果。失败时保留诊断与组临时目录，不自动改用质量模式。

工具查找顺序由 `hugin/hugin_locator.py` 管理：显式路径、`HUGIN_BIN` / `HUGIN_PATH` / `HUGIN_HOME`、项目内 `.runtime-deps/hugin/bin`、系统 `PATH`、常见 Windows 安装目录。没有可用工具时，实验模式会报出搜索路径；高质量模式不需要安装 Hugin。

## 6. 输出、状态与安全约束

- 输出目录由用户选择；默认界面可在源目录下建议 `合成`。JPG 文件名为首张原片名加 `_stack.jpg`；TIFF 使用对应 `.tif` 名称。输出路径不能覆盖任何输入照片，已存在结果时默认拒绝覆盖。
- `FusionResult.actual_backend` 记录实际使用的后端；清单中的 `fusion_backend`、状态、选片路径、参考帧、对齐信息和诊断可用于追查结果。实验模式另外记录 Hugin / Enfuse 命令、退出码及实际输入顺序。
- `archive_enabled` 默认关闭。开启后也必须先得到并验证合成文件，再归档整组原片；合成失败不移动原片。
- SQLite 存储图片、组、任务和分析结果。可复用的分组及选片计划有版本与输入条件约束；恢复任务可从持久状态重建。自动清理只处理数据库确认完成且没有保留标记的私有临时目录，失败和取消的现场保留。
- 队列有容量上限，合成线程默认 1 个、最多 2 个；内存保护会在合成前等待资源。取消信号传入后端及外部进程，避免继续发布未完成结果。

## 7. 配置与扩展

`ApplicationOptions` 接收界面参数；`AppConfig` 分为 `analysis`、`output`、`runtime`、`cache`、`scanner`。常用字段：

| 字段 | 默认值 | 用途 |
| --- | --- | --- |
| `fusion_backend` | `quality` | 选用质量或实验模式 |
| `grouping_pause_seconds` | `20` | 自动分组的拍摄暂停间隔 |
| `minimum_stack_group_size` | `3` | 最小合成组大小 |
| `output.format` | `jpg` | JPG 或 TIFF |
| `output.jpeg_quality` / `jpeg_subsampling` | `100` / `0` | JPG 品质与 4:4:4 采样 |
| `runtime.opencv_aligned_cache_bytes` | `1 GiB` | 质量模式对齐帧缓存上限；名称保留用于旧配置兼容 |
| `runtime.aligned_tiff_cache_bytes` | `512 MiB` | 实验模式已对齐 TIFF 的读取缓存 |
| `runtime.hugin_bin` 等路径 | 空 | 实验模式外部工具位置 |

若增加后端，需实现 `FusionBackend.fuse()` 并返回 `FusionResult`，在 `StackMergeService` 增加显式路由，同时补充模式规范化、界面选项、清单语义和端到端测试。不要把一种模式的失败默认为另一种模式的成功。

## 8. 测试与实图验收

```powershell
pytest -q tests/test_quality_fusion.py tests/test_quality_cache.py tests/test_fusion_backends.py
pytest -q tests/test_pipeline_app.py tests/test_pipeline_recovery.py tests/test_grouping_pause_ui.py
```

质量模式的合成测试覆盖全尺寸输出、清晰边缘、灰色区域零碎标签清理、彩色细节保留、缓存释放及禁止覆盖原片。Hugin 测试覆盖对齐验证、重试、输入顺序和失败时源文件安全；真实 Enfuse 集成用例需要设置 `FOCUS_STACK_ENFUSE`，默认跳过。

本次实图样本为 `F:\相机备份\新建文件夹\1` 中以 DSC03003、DSC03066、DSC03149 开始的三组；以该目录 `合成\快速` 中的对应旧结果作视觉参考。重点查看灰色齿尖、黑色杆与白背景的交界：边缘应连续、没有局部雪花块或明显双线，并保持原图尺寸。实图样本只是回归基线，遇到物体位移、强视差或异常曝光的新组仍应单独检查。

## 9. 运行与故障定位

安装和启动命令见仓库根目录 `README.md`；从源码启动使用 `python main.py`。开发测试建议使用仓库声明的 Python 依赖。实验模式还需确保 Hugin 的两个命令行工具可被发现，例如在 PowerShell 会话中设置 `$env:HUGIN_BIN = 'D:\Program Files\Hugin\bin'` 后启动程序；质量模式不读取该变量。

排查顺序：先看 `stack_manifest.csv` 中该组的 `status`、`fusion_backend`、`selected`、`preview_reference` 与 `diagnostics`，再看输出目录 `.stack_cache/logs` 的运行日志及失败组保留的临时文件。若为 `quality` 的 `PREVIEW_REGISTRATION_REBUILT`，说明恢复任务没有可用的原始预览矩阵尺寸，已重新配准。若为 `hugin_enfuse` 的 `ALIGNMENT_LEVEL_*_FAILED`，按实际输入顺序、裁切比例与对应尝试目录检查 Hugin；`HuginToolNotFound` 则检查工具发现路径。修复代码后应重新合成受影响组，旧输出不会自动更新。
