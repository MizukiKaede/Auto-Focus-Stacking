# Focus Stack Assistant 修改任务（最终版）

## 背景与约束

系统有两种合成模式：

- `quality`：主体画质基本正常，只有白底平坦区域偶尔出现雪花状斑块。
- `hugin_enfuse`：物体边缘有锯齿，而且发糊。

Quality 模式使用全尺寸对齐图、焦点标签和窄边界 RGB 融合，`blend_focus_pyramid()` 默认 `levels=1`。现有的中性色标签稳定化规则是：灰度 < 235、通道差 < 65，再做 15×15 中值滤波。

典型输入：单张 40MP～60MP，每组几十张，主要在 HDD 上运行。

**目标：** 不重写已经正常的主体融合，只做以下几件事：

1. 修复 Quality 的白底雪花；
2. 修复 Hugin 的边缘模糊和锯齿；
3. 降低高像素、大组照片的峰值内存；
4. 在不牺牲画质的前提下提速；
5. 硬件加速优先用 OpenCL（T-API），不绑定 CUDA。

**不变的原则：**

- 一种后端失败后，不得静默切换到另一种后端；
- 合成结果验证成功之前，不得移动原片；
- 所有改动都要能回退，并且能做 A/B 对比。

---

## P0：诊断与量化基线（先于任何算法修改）

### P0.1 固定测试集
至少包括：白底产品、黑杆或黑白高反差边缘、灰色齿尖、40MP 样本、60MP 样本、40 张以上的大组、1 组困难样本（有物体位移或明显视差）。

基线输出放在独立目录，不要写进正式输出目录。同时记录 OpenCV、Hugin、Enfuse 的版本和配置快照，以及机器的物理内存大小、临时目录在 SSD 还是 HDD 上。

### P0.2 性能 profile
- Quality 分阶段计时：JPEG 读取、解码、warp、焦点响应、标签与正则化、融合、编码。
- Hugin 分阶段计时：`align_image_stack`、TIFF 写入、TIFF 读取、Enfuse。
- 同时记录：总耗时、峰值内存、读写字节数、worker 数。

**并发：** 先在源码中确认当前的默认和最大合成并发数。不要擅自修改配置上限。

用 worker = 1、2、3、6分别测试，记录：总耗时、每小时处理组数、单组延迟、峰值内存、HDD 吞吐、I/O 等待。

后续允许根据内存预算限制实际并发（`effective_workers`），但每次限制都要写入日志并说明原因。

### P0.3 白底雪花指标
在固定的白底 ROI 中统计：小连通块数量、瑕疵总面积、最大连通块面积。

### P0.4 边缘指标
在固定的关键 ROI 中统计：双线得分、边缘锐度、晕边宽度。

### P0.5 指标噪声底
同一组重复运行，测出雪花数量、面积和边缘指标的自然波动。后面所说的"改善"，必须超过这个波动。验收不能只靠肉眼。

### P0.6 Hugin 链路记录
每次运行都记录：`align_image_stack` 的完整参数（包括是否带 `-m`）、实际输入顺序、重试参数、Enfuse 层数、hard-mask 状态、临时 TIFF 的位深和总大小。

保存至少 1 组出问题的样例，包括对齐后的 TIFF、焦点蒙版和最终输出。

### P0.7 配准残差诊断
只加诊断，不改配准：对 Quality 模式在原图上测量 warp 后的残差（取若干高纹理 ROI，用 ECC 或相位相关），写入 diagnostics。

## P1：Quality 白底修复

分两步做：先做亮度一致化，再加纹理门禁。每一步单独做 A/B。

亮度一致化解决的是"换了来源帧为什么看得出来"，纹理门禁解决的是"白底为什么会乱换来源帧"。两者是前后两层问题，不能互相替代。

### P1.1 逐帧亮度一致化
以参考帧为基准，对每个选中帧估计一个全局亮度增益。第一版只做增益，不改色相。

**估计增益：**
- 只在有效重叠区、低梯度区域、非过曝和非欠曝的像素上，计算参考帧与当前帧的稳健亮度比，例如取中位数或截尾均值；
- 不要用整图平均值；
- 增益要限定在合理范围内，每帧的实际增益写入 diagnostics。

**应用增益：**
- 在浮点域里乘上增益，再裁剪回原来的取值范围；
- 高光要特别检查：增益大于 1 时，白底不能被截断到 255 后出现新的色阶断层。

**和焦点响应的关系：** 焦点响应和噪声底都在增益校正后的帧上计算，保证门禁判断的尺度一致。

完成后立即跑基线，记录雪花指标和边缘指标，确认单靠亮度一致化解决了多少问题。同时检查主体区域的亮度和锐度，变化不能超出噪声底。

**可选的第二步：** 只有全局增益明显不够，而且样本证明存在明显的暗角伸缩时，才实验低阶亮度面（例如低阶二维多项式）。第一版不做局部曝光校正，以免把物体真实的明暗结构拉平。

### P1.2 纹理与对比度门禁
先在源码中确认：240～255 的真实白底，是不是正因为 `gray < 235` 被排除在稳定化之外。确认结果写进报告。

新增语义化的平坦区判断，依据是局部纹理或方差、最大焦点响应、噪声底。噪声底按亮度分段估计，白底和暗部分别有各自的噪声水平。

"低纹理且没有可靠的焦点证据"的区域，不再让几十张帧竞争来源，直接使用参考帧。

现有的中性色规则暂时保留以兼容旧行为，但不再作为白底保护的主要依据。

### P1.3 统计量从一开始就按流式设计
P3 会改成两遍流式扫描，所以 P1 不能依赖"整组全分辨率焦点响应图同时放在内存里"。

- 平坦区和纹理门禁的统计，默认在长和宽各缩小一半的尺寸上计算，约为原图像素数的 1/4；
- 统计图设置像素上限，约 10～15MP；
- 统计结构必须支持逐帧更新，比如当前最大响应、对应帧号、纹理统计，将来可以直接搬进流式处理；
- 焦点标签本身的最终归属仍然按全分辨率决定。

### P1.4 边缘保护
不能简单地把所有平坦区都锁定到参考帧，因为主体边缘附近的参考帧可能带着失焦晕边。

做法：生成可靠边缘蒙版，再膨胀出一圈安全带。安全带内禁止锁定参考帧。

### P1.5 锁定区边界过渡
锁定区和正常焦点区之间只做窄过渡，用来消除亮度校正后仍然残留的微小接缝。

### P1.6 阶段检查点
完成亮度校正、门禁、边缘保护和边界过渡后，先跑一次完整测试。这一次不做连通域清理。

记录：雪花数量和面积、双线、晕边、耗时、峰值内存。

### P1.7 连通域清理
最后才清理很小的孤立标签块，并入周围的主导标签。

清理前后的结果分别保存、分别计算指标，用来确认雪花主要是被门禁解决的，而不是被清理步骤掩盖的。

### P1 退出条件
阈值由 P0 的噪声底得出，不硬编码百分比。

- 雪花数量和面积的改善超过自然波动；
- 任何一组正常样本的边缘指标恶化不超过噪声底；
- 没有新增明显的晕边，主体锐度没有明显下降。

## P2：Hugin 边缘模糊和锯齿

P2 和 P1 是不同的代码路径，P0 完成后可以并行开发。但 **P2.4 里复用 P1 门禁的部分，必须等 P1.6 验证通过后才能做。**

当前链路：`align_image_stack` → 对齐后的 TIFF → 焦点蒙版 → Enfuse。

### P2.1 同组双后端对照
对同一组选片，分别用 Quality 和 Hugin 合成，比较完全相同的 ROI。

### P2.2 检查对齐后的 TIFF
如果对齐后的 TIFF 本身已经有边缘错位、双线或缩放不一致，问题出在 Hugin 对齐，按以下顺序调整：

1. `-m`（视场和缩放优化，用来补偿对焦呼吸）；
2. 输入顺序；
3. 相关性和控制点参数；
4. 重试策略。

这种情况下先不要改 Enfuse。

**不要默认改用 Quality 的变换矩阵生成对齐 TIFF。** 那样会改变实验模式的语义，需要单独决策。

### P2.3 检查焦点蒙版
如果 TIFF 对齐正常，但蒙版本身有锯齿，先确认 Hugin 模式是否和 Quality 共用同一套焦点标签、平坦区稳定化和蒙版正则化代码。

### P2.4 修蒙版
- 如果没有共用，就把 P1 中已经验证有效的门禁和平坦区逻辑复用到 Hugin 的蒙版生成里，避免维护两套平坦区判断；
- 然后清理小的凸起，对边界做抗锯齿，只在边界带做 1～2px 的窄羽化；
- 不要对整张蒙版做 GaussianBlur。

### P2.5 Enfuse 发糊
只有对齐后的 TIFF 和蒙版都正常、最终输出仍然发糊时，才做以下 A/B：
- 当前层数 vs 更少的层数；
- hard-mask vs hard-mask 加窄过渡。

不要默认去掉 hard-mask。

### P2.6 临时 TIFF
- 机器有 SSD 时，Hugin 临时目录优先放在 SSD 上；
- 只有 HDD 时，不要增加临时 TIFF 的数量，也不要增加并行的 Hugin 任务；
- 之后再对比无压缩、LZW、Deflate 三种方式，以整条流程的总耗时为准，不看文件大小。

## P3：Quality 两遍顺序流式扫描

P1 画质稳定后才开始。

**目标：** 峰值内存只和单张图的尺寸有关，不再随组内张数线性增长。

### 读取方式（适用于 P3 及之后所有 Quality 路径）
- 每张 JPEG 一次性整体读进内存（顺序读），再用 `cv2.imdecode` 解码；
- 设置全局读盘并发上限，默认同时只有 1 个 worker 在读 HDD，解码和计算不受这个限制。

### Pass 1（参考帧最先处理）
逐帧执行：读取 → 解码 → 估计并应用亮度增益 → warp → 计算焦点响应 → 更新统计量和标签 → 释放当前帧。

### 中间处理
依次做：纹理门禁、平坦区锁定、边缘保护、边界过渡、标签正则化、连通域清理。

### Pass 2
逐帧执行：读取 → 解码 → 应用和 Pass 1 相同的增益 → warp → 按最终标签和权重累加 RGB → 释放当前帧。

累加器利用硬标签的特点来省内存：只有一个来源的像素直接写入 uint8 输出，只在过渡带里用浮点累加。

### 等价性验收（强制）
把"包含 P1 改动的整组内存实现"保留为参考实现。同一组输入分别跑内存版和流式版，比较：
- 逐像素最大误差和平均绝对误差；
- PSNR；
- 关键 ROI 的差异；
- 最终 JPEG 或 TIFF 的观感。

理想情况是逐像素一致。如果浮点运算顺序导致微小差异，必须事先定义一个很小的容差。"肉眼看起来差不多"不能作为唯一标准。

同时记录第二次解码和第二次 warp 带来的额外耗时。只有峰值内存大幅下降、总耗时增加在可接受范围内，才把流式版设为默认路径。

### 并发与内存预算
实测单个 worker 在 60MP 下的峰值内存，然后按"可用内存 ÷ 单 worker 峰值"计算 `effective_workers`，并写入日志。

## P4：OpenCL（T-API）硬件加速

优先用 OpenCL，不做 CUDA。理由：
- pip 安装的 `opencv-python` 不含 CUDA 模块，用 CUDA 需要自行编译，打包和分发成本高；
- NVIDIA 显卡同样可以运行 OpenCL。

### P4.1 运行时检测
启动时检查并记录 `cv2.ocl.haveOpenCL()`、`cv2.ocl.useOpenCL()` 和实际使用的设备。

OpenCL 不可用时自动退回 CPU，不能因此报错导致软件无法使用。

### P4.2 逐项实测
分别测试以下操作：resize、warpAffine、warpPerspective、GaussianBlur、Laplacian、Sobel、焦点响应、权重运算、融合累加。

不要假设用了 UMat 就一定更快，只保留实测有收益的环节。

**特别确认：** `INTER_LANCZOS4` 的 warp 在 OpenCL 下是否真的走 GPU，还是退回 CPU 执行。

### P4.3 避免数据来回传输
目标流程：CPU 解码 → 上传到 UMat 一次 → warp → 焦点计算和滤波 → 融合和统计 → 必要时再下载回 CPU。

不要出现 Mat → UMat → Mat → UMat 这样的反复转换。

### P4.4 CPU 和 OpenCL 结果一致性
每个改用 GPU 的环节，都要比较 CPU 和 OpenCL 的 warp 插值、焦点响应、标签和最终 RGB。

如果结果和当前 CPU 实现不完全一致，不能悄悄改变画质。要单独做 A/B，必要时这一环节继续用 CPU。

### P4.5 显存预算
60MP 的 float32 RGB 一帧约 690 MiB。多个 worker 共用 GPU 时要设显存上限，超出时让出 GPU 或者改走 CPU，不能因为显存不足而失败。

### P4.6 何时值得启用
只有 profile 显示 warp、焦点计算、融合占了主要耗时，OpenCL 才作为默认加速的候选。

如果瓶颈在 HDD 读取和 JPEG 解码，就不要指望 OpenCL 能让整体提速好几倍。

## P5：虚拟缓存和分块处理（按 profile 决定）

暂时不做。

- **虚拟缓存：** 只有两遍流式扫描仍然不能满足需求，或者某些计算成本高的中间结果需要反复读取时，才考虑。形式为"单个大缓存文件加一个小索引"，用顺序的大块读写，不要生成大量零散的 TIFF。压缩方式对比无压缩、LZ4、低等级 Zstd，以总耗时为准。Hugin 的 TIFF 缓存和 Quality 的缓存不要合并。
- **分块处理：** 不要直接对 JPEG 分块。只有已经有了解码后的中间数据，才测试 1024、2048、4096 三种块大小；块之间的重叠必须覆盖所有空间算子的作用半径。

## 版本与恢复

- 如果 P1 的改动（亮度增益、焦点标签、平坦区结果）会写入 SQLite 或恢复缓存，要立即增加对应的版本号（`focus_measure_version` 或 `focus_regularization_version`），防止旧任务复用旧标签。
- 统一 `minimum_stack_group_size`：文档里一处写 3，一处写 4。以源码实际默认值为准，同步修正文档。

---

## 暂时不改

Quality 主体目前正常，以下内容先不动：
- 把 640px 配准改成从粗到细的多级配准；
- 相似、仿射、单应三种模型的自动选择；
- 全分辨率配准精修；
- 大规模重写金字塔融合；
- CUDA 后端；
- nvJPEG。

640px 路径只加 P0.7 的残差诊断。等出现明确的双线、重影或错位证据后再处理。

## 优先级

| 阶段 | 内容 |
| --- | --- |
| P0 | profile、量化指标及噪声底、Hugin 链路记录、配准残差诊断 |
| P1 | 亮度一致化（单独测试）→ 纹理门禁 → 边缘保护 → 边界过渡 → 检查点 → 连通域清理 |
| P2 | Hugin 按对齐、蒙版、Enfuse 三层定位并修复（P0 后可和 P1 并行，P2.4 等 P1.6） |
| P3 | 两遍顺序流式扫描、读盘并发控制、等价性验收、按内存预算确定实际并发 |
| P4 | OpenCL，只加速 profile 证明值得的热点 |
| P5 | 按 profile 决定是否做虚拟缓存和分块处理 |
