# Auto Focus Stack Assistant · main 常规版

Auto-stack 是一个自动批量图片合成的 Windows 桌面应用，面向焦点堆栈摄影。导入一批照片后，程序自动扫描和分组、分析清晰覆盖、选择有用帧并对齐合成，为各组分别生成结果。

项目使用 Python 和 PySide6 编写，重点关注大批量照片处理时的内存占用、任务并发和过程恢复能力。

适用于有大批量商业图片需要合成，并且在前期拍摄时**没有按照焦点顺序**进行拍摄。

## 自动分组：一批照片怎样拆成多个合成任务

程序面向同一主体、构图基本不变、焦点逐步变化的拍摄序列。选择照片目录后，会先扫描、自动分组，再在每组中选出有用的清晰帧，分别生成合成结果。**当前分组不要求固定张数，也不按文件名前缀或子文件夹名称直接划组。**

### 1. 扫描与排序

- 图形界面默认只读取所选目录中的 `.jpg` / `.jpeg`，不递归读取子目录。程序接口/配置支持 `recursive` 递归扫描；开启后会把子目录照片也放入同一排序序列。
- 有 EXIF 拍摄时间的照片优先按拍摄时间排序；时间相同时按文件名、路径的自然顺序排序。
- 没有拍摄时间的照片放在有时间的照片之后，按文件名、路径自然排序，例如 `IMG_2.jpg` 在 `IMG_10.jpg` 前。没有时间时，拍摄间隔规则无法生效，仍会比较画面。

### 2. 逐张比较相邻照片，确定组边界

默认入口使用 `StackGroupDetector`。它读取长边不超过 640 像素的 RGB 预览，进一步缩小并模糊后比较低频构图与颜色，尽量减少正常焦点变化带来的细节差异。遇到下列任一情况，就从当前照片开始新组：

| 边界条件 | 当前默认行为 |
| --- | --- |
| 预览图形状改变 | 如横竖幅切换、宽高比改变，开始新组 |
| 拍摄时间倒退 | 相邻照片都有可用时间且出现负间隔时切分 |
| 长时间停拍 | 间隔 **超过 60 秒** 时强制切分；如果“分组拍摄间隔”设得大于 60 秒，则改为超过该设置值 |
| 构图明显变化 | 模糊预览的构图差异分数大于 `0.025`，即使没有停拍也切分 |
| 停拍后画面略有变化 | 间隔达到“分组拍摄间隔”（默认 **20 秒**），且构图差异分数大于 `0.006` 时切分 |
| 白底孤立主体明显变化 | 在大面积明亮中性背景、可识别孤立较暗主体的画面中，额外检查主体区域；明显位移、转面或外形变化也会切分，并容忍小幅对焦呼吸与位移 |

`0.025` 和 `0.006` 是程序内部的归一化画面差异分数，不是物体位移百分比。**停拍 20 秒本身不会必然分组**：20～60 秒范围内还需要画面变化；默认超过 60 秒才会仅凭时间强制切分。分组比较的是相邻照片，不能保证识别所有缓慢变化或同构图重复拍摄。

例如：同一主体连续拍摄 30 张，正常焦点变化且构图差异未越过门槛时，会保持一组；更换主体或转面后通常会切出下一组；默认停拍 65 秒再拍，即使构图相近也会开始新组。可在界面调整“分组拍摄间隔”，让它更符合自己的拍摄节奏。

### 3. 分组以后，还会判断是否需要合成

“找到一组”不等于“这一组必定合成”。界面的“最少相似照片数”默认为 **4 张**，可自行调整；少于该值的组会分类记录，不进入融合。

达到张数要求后，当前默认选片流程在长边 1280 像素的预览上执行：

1. 计算各帧的全画面焦点评分，选择评分最高的一帧作为参考。
2. 使用仿射 ECC 配准，把其他帧的预览对齐到参考坐标；配准失败的帧记录原因，不作为有效选片候选。
3. 比较每个有效细节位置在各帧中的清晰度。达到该位置最佳清晰度 **90%** 的位置计入该帧的清晰覆盖。
4. 逐次选择能补充最多未覆盖细节的帧；新增覆盖低于 **0.05%**，或总覆盖达到 **99.95%** 时停止，并保证参考帧保留。这里的百分比基于预览中有效细节区域，不是最终图片质量评分。
5. 至少要有两张被选中的帧，且有效组张数仍达到最小要求，才提交合成；只有一张有效选片的重复组不会强行融合。选片阶段还会检查主体明显变化和预览尺寸一致性。

因此，一组 30 张照片最终可能只使用其中部分照片：其他帧的清晰区域已经被覆盖，并不表示这些文件被删除。三种引擎使用相同的分组与选片结果，切换模式主要改变后面的对齐、选源与融合方式。

### 4. 需要固定分组时

可在所选照片目录根部放置 `stack_groups.json`，用文件名显式指定照片组：

```json
{
  "groups": [
    ["IMG_0001.jpg", "IMG_0002.jpg", "IMG_0003.jpg", "IMG_0004.jpg"],
    ["IMG_0005.jpg", "IMG_0006.jpg", "IMG_0007.jpg", "IMG_0008.jpg"]
  ]
}
```

每个内层数组是一组，显式分组优先于自动分组；未列出的照片仍按连续片段自动分组。文件名匹配不区分大小写，不能填写目录路径，也不能在配置中重复填写同一个文件名。递归扫描存在重名文件时，应拆开目录运行，避免只凭文件名产生歧义。显式分组仍会经过最小张数、选片和对齐检查。

实现入口：[扫描排序](focus_stack_app/core/scanner.py)、[默认分组](focus_stack_app/core/group_detector.py)、[手动分组](focus_stack_app/core/manual_groups.py)、[组内选片](focus_stack_app/core/whole_frame_selection.py)。

## 三种合成模式怎样工作

在界面的“高级与性能设置 → 合成引擎”中选择模式。默认是**高质量合成引擎**。共同流程为：

**扫描照片 → 自动/显式分组 → 预览配准与清晰覆盖选片 → 所选引擎合成 → 编码保存**

| 模式 | 对齐与焦点判断 | 融合方式 | 使用侧重点 |
| --- | --- | --- | --- |
| 高质量（`quality`，默认） | 复用预览变换，对原图执行全分辨率变换；在全分辨率分析焦点归属 | 稳定焦点标签、材质色调与印字/外沿，再做窄过渡融合 | 细小纹理、印字和材质边缘 |
| Fast（`fast`） | 复用预览变换，在默认长边 1600 像素的代理图上主要确定来源 | C++ 核心逐帧全分辨率渲染，结合局部边缘修复与窄接缝处理 | 批量任务中减少全分辨率重复处理 |
| 实验（`hugin_enfuse`） | Hugin 独立对齐并输出 TIFF，程序再检查与细化几何关系 | 程序生成全分辨率焦点硬蒙版并修正边缘/色调，由 Enfuse 渲染 | 比较另一套对齐与融合流程，接受更多中间文件 |

### 高质量模式：全分辨率焦点归属与边缘一致性

1. **对齐原图**：把组内选片阶段得到的变换按坐标比例映射到原图，逐帧变换到参考图的全尺寸画布；当前常规路径使用 OpenCV Lanczos 插值。预览对齐参数缺失的恢复任务会重新建立配准。
2. **计算焦点归属**：在全分辨率对齐图上比较局部清晰度，为每个位置决定使用哪一帧；结合背景稳定与有效来源检查，减少低纹理区域的随机选源和变换边界的无效取样。
3. **稳定标签与色调**：当前默认配置启用纹理/平坦区域判定、印字边缘保护、主体外沿归属及材质色调协调，针对雪花斑、色块、印字晕边和外沿混入失焦背景等问题进行处理。这些规则用于降低伪影，不能保证所有场景都消除伪影。
4. **融合与保存**：按焦点标签逐帧累积 RGB，默认采用约一像素的窄过渡、单层混合，避免把大范围失焦低频层混入清晰轮廓。使用受内存预算限制的缓存；内存或缓存不足时可能重新读取/变换部分帧，最后按输出设置保存 JPG 或 TIFF。

高质量模式不调用 Hugin/Enfuse。它的重点是全分辨率细节和边缘处理，相应地需要较多计算与内存；“全分辨率”指在原图尺寸上处理，预览阶段的配准误差仍可能影响结果。

### Fast 模式：代理图选源，一次全分辨率渲染

1. **复用选片和坐标**：直接使用共同分析阶段选出的照片、参考帧与变换，不另做 Hugin 对齐。
2. **在代理图上确定来源**：默认长边 1600 像素，计算焦点特征与来源标签；低纹理区域优先锁定参考帧，并处理材料边缘、印字、小孔与相邻细节的归属。
3. **逐帧渲染原图**：保留压缩输入数据，随后每张被选中的原图最多执行一次完整 RGB 解码与双三次插值变换。C++ 核心将像素写入目标，另外执行局部全分辨率边缘判定与材质色调修正。
4. **处理接缝与保存**：主要区域按来源标签取样，在来源切换处使用默认半径 2 像素的窄接缝过渡，再编码输出；它不会把所有区域都改成大范围柔化。

Fast 的减少计算来自“先在代理图上选源，再渲染原图”。细于代理图尺度的细节可能受影响，适合批量处理后检查细小印字、孔洞和外沿。本次发布没有整批速度实测，不能保证任何照片组都比高质量模式快。

### 实验模式：Hugin 对齐，程序蒙版，Enfuse 渲染

1. **独立对齐**：对共同流程选出的帧调用 `align_image_stack`，生成裁剪到共同有效区域的对齐 TIFF。程序检查 TIFF 数量、可读性、尺寸、主体变化和裁剪比例；可重试的对齐失败会尝试调整输入顺序或对齐参数，持续失败则记录失败。
2. **残差细化**：当前默认流程在 Hugin 对齐结果上尝试受限的仿射 ECC 微调。相关性、位移与缩放必须通过门槛；若任一非参考帧未通过，整组保留 Hugin 原坐标，避免混用原坐标与微调坐标。
3. **由程序决定焦点**：默认使用 `quality` 焦点蒙版配置，在全分辨率比较焦点并生成每帧对应的 0/255 硬蒙版，同时处理纹理、印字、外沿归属和材质色调。必要时写出经过坐标/色调修正的中间 TIFF。
4. **由 Enfuse 渲染**：将这些图像与硬蒙版交给 `enfuse --load-masks`。当前焦点堆栈配置中，对比度权重为 1，曝光、饱和度、熵权重均为 0。默认开启材质修正时自动选择单层融合；关闭相关修正或使用其他配置后，可按色调漂移选择更多层数。最后检查输出并按用户设置编码。

因此，当前实验模式包含 Auto-stack 自己的焦点判断与修正，不只是直接运行 Enfuse 的默认自动蒙版。它会产生对齐 TIFF、蒙版和可能的修正 TIFF，磁盘占用与读写通常更多；输出画幅也可能因共同有效区域裁剪而变小。便携版已内置工具，从源码运行则需要可用的 Hugin/Enfuse。

### main 与 dev 在这些流程中的差别

两版的默认扫描、分组、选片规则相同，上述三种模式的总体流程也相同。main 对应常规发布入口；dev 在此基础上增加原生线程预算与异常降级，并调整 Hugin 的部分算子和任务调度：

- dev 的 Quality/Fast 原生库无法加载时，会记录原因并转用对应的 NumPy/OpenCV 实现，耗时可能增加；这不是切换到另一种合成模式。
- dev 把部分 Hugin 外沿、纹理统计与硬蒙版操作交给 C++，蒙版任务按默认进程共享的 12 CPU 预算和内存准入安排。
- dev 的残差 ECC 在每个组内逐帧串行执行，不同组仍可并行；两版均保留残差验收与整组回退规则。

分支差异不构成效果或速度保证。上述说明依据当前实现，已发布便携版只做过启动与依赖加载检查。

实现入口：[高质量/Hugin 引擎](focus_stack_app/fusion/backends.py)、[Fast 引擎](focus_stack_app/fusion/fast_backend.py)、[Fast 渲染](focus_stack_app/fusion/fast_fusion.py)、[Enfuse 与焦点蒙版](focus_stack_app/hugin/enfuse.py)。

## 项目结构

```text
focus_stack_app/
├── core/       核心分析、分组、质量和选帧逻辑
├── files/      文件归档与命名冲突处理
├── fusion/     图像融合与焦点蒙版
├── hugin/      Hugin / Enfuse 集成
├── pipeline/   任务队列、工作线程和流程控制
├── storage/    数据库、清单和缓存
├── ui/         PySide6 图形界面
└── utils/      图像、EXIF、日志和资源工具
tests/          自动化测试
```

三种模式共用扫描、分组和选片。从源码运行时，界面中的“实验模式”需要可用的
`align_image_stack` 与 `enfuse`；程序会按显式路径、`HUGIN_BIN` 等环境变量、
项目自带运行时和系统路径查找。旧配置值 `opencv` 仍映射到高质量模式；`fast` 现在选择独立的 Fast 模式。

Fast 使用随项目附带的 Windows 64 位 `fast_core.dll`，版本为 `fast-cpp-v4-print-statistics`；
原高质量、Hugin/Enfuse 的算法及默认参数保持不变。

完整实现与系统说明见 [技术文档](docs/技术文档.md)、[技术架构](docs/技术架构.md) 及 [重构UI说明](docs/重构ui.md)。
